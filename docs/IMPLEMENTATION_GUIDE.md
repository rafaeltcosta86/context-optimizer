# Implementation Guide — `context-optimizer`

**Audience:** The Claude Code agent who will build `context-optimizer` v1.0 from this specification.
**Companion documents:** `PRD.md` (what), `ARCHITECTURE.md` (design), `COMPETITIVE_ANALYSIS.md` (boundaries)

This document tells you **how to build** the skill: in what order, which specialist skills to invoke at which step, what to validate before moving to the next step, and how to recover from common failure modes.

> **Scope:** **v1.0 (Claude Code skill)** is fully covered below. v1.1 (Cursor port) and v1.2 (Gemini/Antigravity port) are summarized in §8 — execute them after v1.0 is shipped and validated. **v2.0 (organic memory growth) is explicitly out of scope of this guide** — see `PRD.md` §12.2 and `ARCHITECTURE.md` §13 for the deferred design; do not attempt v2.0 until v1.0 is in community use.

## 1. Definition of Done (top-level)

`context-optimizer` is ready to release when **all of the following are true**:

1. The skill file (`skill/context-optimizer.md`) is present, well-formed, and contains the procedure described in `ARCHITECTURE.md` §2
2. The skill embeds the `Known Patterns` library (`ARCHITECTURE.md` §6) — at least the 10 patterns listed for v1.0
3. The skill, when invoked on the 3 reference project types (`PRD.md` §2.4), produces correct output:
   - Project A (workflow-heavy): generates dynamic-in-flight hook + memory files + canonical-source dedup recommendations
   - Project B (multi-agent): generates per-platform adapters with caveat lines
   - Project C (weak state): triggers the 3-question fallback dialog
4. Every recommendation generated by the skill includes both token cost and estimated savings (no silent ROI filtering)
5. `context-spec.md` is produced on every implementation phase with the structure documented in `ARCHITECTURE.md` §2 Phase 5
6. All 8 PRD success criteria are objectively verifiable on the reference projects
7. The repository is git-initialized, has an MIT LICENSE, and a public-facing README following the positioning in `COMPETITIVE_ANALYSIS.md` §6
8. Generated files for Cursor and Gemini include the mandatory caveat lines

### Build Phase 2 — Skill file skeleton

**Goal:** A `skill/context-optimizer.md` file that conforms to Claude Code skill format, declares the procedure, and is invocable (even if the procedure is incomplete).

**Steps:**

1. Invoke `skill-creator:skill-creator` to get the canonical skill format and current best practices.
2. Author the skill frontmatter:
   ```yaml
   ---
   name: context-optimizer
   description: Use this skill to scan any project and recommend token-efficient improvements to how new AI agent sessions receive context. Supports Claude Code, Cursor, and Gemini CLI / Antigravity. Use when starting work on a project that doesn't have well-structured session-start context for AI agents.
   ---
   ```
3. Author the skill body sections in this order (each section anchors a phase from `ARCHITECTURE.md` §2):
   - `## Purpose` — single paragraph matching the description
   - `## When to Use This Skill` — bullet list of trigger situations
   - `## What This Skill Does NOT Do` — paste the Out of Scope summary from `COMPETITIVE_ANALYSIS.md` §4
   - `## Golden Rule` — the token-efficiency commitment (`PRD.md` §3 "Key behavioral commitments")
   - `## Procedure` — the 5 phases, each as a subsection (`### Phase 1 — Scan`, etc.) with the procedure from `ARCHITECTURE.md` §2 transcribed in second-person imperative (instructions to the future agent invoking the skill)
   - `## Per-Agent Adapters` — Claude Code / Cursor / Gemini CLI sections matching `ARCHITECTURE.md` §5
   - `## Known Patterns` — the table from `ARCHITECTURE.md` §6, expanded per pattern with: name, one-line description, trigger condition, rationale, example application
   - `## Output Format` — exact `context-spec.md` structure from `ARCHITECTURE.md` §2 Phase 5
   - `## Constraints (Hard Rules)` — the constraint list from `ARCHITECTURE.md` §10
4. At each subsection, write *for an agent who will read this skill cold*. Use second-person ("you scan", "you recommend") not third-person ("the skill scans"). The skill body is read by an executing agent — clarity is paramount.
5. Length budget: target ~600-900 lines in the final skill file. If significantly longer, consider extracting Known Patterns to a sibling file (`known-patterns/v1/*.md`) and referencing them.

**Definition of Done for Build Phase 2:**
- [ ] Skill file conforms to Claude Code's skill format (validated by `skill-creator:skill-creator`)
- [ ] All 5 phases documented in the procedure section
- [ ] All 10 Known Patterns documented
- [ ] All hard constraints (`ARCHITECTURE.md` §10) restated in the skill body
- [ ] Skill is invocable: `/skill context-optimizer` loads it without errors

**Common pitfalls:**
- Writing the skill body in third-person — confuses the executing agent
- Skipping the `What This Skill Does NOT Do` section — leads to scope creep at invocation time
- Embedding Known Patterns inline when the file gets too long — extract to sibling files instead

### Build Phase 3 — Reference project preparation

**Goal:** Three minimal reference projects to validate the skill against (per `PRD.md` §2.4).

**Steps:**

1. Inside `examples/`, create three subdirectories:
   - `examples/project-a-workflow-heavy/` — minimal `git init`-ed directory with: a `CLAUDE.md` with no startup section, an `AGENTS.md` with workflow rules, GitHub Actions yml stub showing sequential job dependencies, sample issues data (you can copy structure from the user's `agentic-pdlc` repo without copying private content)

2. For each, create a `before/` snapshot capturing the project state. Do not yet create `after/` — that is produced by running the skill in Build Phase 4.

**Definition of Done for Build Phase 3:**
- [ ] All three reference projects present
- [ ] Each is a self-contained git repo (or at least a directory the skill can be invoked from)
- [ ] `before/` snapshots committed

**Common pitfalls:**
- Copying real private content from a working project — use the *structure* of `agentic-pdlc` but create synthetic content
- Making the reference projects too complex — they need to exercise the skill's branches, not be realistic full projects

### Build Phase 4 — End-to-end validation

**Goal:** Verify all 8 PRD success criteria on the reference projects.

**Steps:**

1. Invoke the skill on each reference project from a new Claude Code session.
2. For Project A (workflow-heavy):
   - Verify recommendations include: Layer-0 startup-guide expansion, dynamic-in-flight hook, canonical-source dedup
   - Verify `context-spec.md` is produced
   - Measure tokens spent in the first 2 turns of a *new* session after applying recommendations → confirm SC-1 (≥60% reduction)
3. For Project B (multi-agent):
   - Verify recommendations cover both Claude Code AND Cursor
   - Verify generated `.cursor/rules/*.mdc` or `.cursorrules` includes the mandatory caveat line
   - Confirm SC-4 (multi-agent coverage)
4. For Project C (weak state):
   - Verify the skill enters the 3-question fallback dialog (does not generate weak recommendations from insufficient signals)
   - Confirm SC-5 (weak-scan resilience)
5. Across all three:
   - Confirm SC-3 (audit trail) — every applied recommendation appears in `context-spec.md`
   - Confirm SC-6 (no silent ROI gatekeeping) — every recommendation in output includes both numbers
   - Confirm SC-7 (Layer 3/4 separation) — manual inspection of generated files
   - Confirm SC-8 (caveat present in all cross-agent files)
6. Capture `after/` snapshots in `examples/<project>/after/`.

**Validation report:** Create `docs/VALIDATION_REPORT.md` listing each success criterion with the project on which it was verified, the test method, and the observed result.

**Definition of Done for Build Phase 4:**
- [ ] All 8 success criteria objectively verified (not assumed)
- [ ] `examples/<project>/after/` snapshots captured
- [ ] `docs/VALIDATION_REPORT.md` committed
- [ ] No success criterion is marked "pass" without a documented test

**Common pitfalls:**
- Eyeballing token reduction — actually count tokens (or use a token counter on file sizes — approximation OK if methodology is documented)
- Claiming "behavior verified for Cursor/Gemini" — you cannot verify their behavior from inside Claude Code; the caveat line is the only verification needed for v1

## 4. Validation Gates (between phases)

Between each Build Phase, run this validation gate before continuing:

| Question | If "no" → action |
|---|---|
| Did I complete every step in this Build Phase's checklist? | Go back; do not advance |
| Did I invoke the specialist skill(s) for this phase? | Invoke now; revise work based on skill's guidance |
| Is the work idempotent (re-running it doesn't change state)? | Fix idempotency before advancing |
| Have I committed the work to git? | Commit now |
| If a user asked me to demonstrate this phase's output, could I do it without further work? | Address the gap |

**Why gates matter:** The 5 phases compound. A missed step in Phase 2 surfaces as a bug in Phase 4 — much more expensive to fix. Treating gates as optional defeats the structure.

## 5. Common Failure Modes and Recovery

These are mistakes anticipated from the design phase. If you hit them, here's how to recover.

| Symptom | Likely cause | Recovery |
|---|---|---|
| Skill body grew past ~1,200 lines | Embedded too much in the main skill file | Extract `Known Patterns` to sibling files in `known-patterns/v1/`, reference them from skill body |
| Reference project A doesn't trigger the dynamic-in-flight recommendation | Detection signals not matching project structure | Re-read `ARCHITECTURE.md` §4; verify the multi-signal heuristic matches the project's actual signals |
| Cursor caveat line missing from generated file | Adapter recipe in skill body didn't include the caveat | Update the Cursor adapter recipe to include the caveat as a hard-coded prefix; never make caveats conditional |
| `context-spec.md` doesn't include "Ad-hoc recommendations" section | Skill applied recommendations not mapped to Known Patterns without flagging | Add `ad-hoc` tagging logic to the recommendation generation phase |
| Re-running the skill produces a new diff on an unchanged project | Idempotency violated — likely in the merging logic of CLAUDE.md edits | Diff the two outputs; identify the non-idempotent step; fix at the source (don't add a comparison check after the fact) |
| Generated `CLAUDE.md` overwrites user's existing content | Adapter recipe used `Write` instead of `Edit` with non-destructive merge | Change to `Edit` with explicit existing-content preservation; never use `Write` on a file that exists with user content |
| Weak-state fallback triggers on a project that has plenty of signals | Signal-counting threshold is wrong, or signals not being recognized | Re-read `ARCHITECTURE.md` §4 and Phase 3 step 1; verify the signal-counting logic |

## 6. Installation (the v1 user path)

The implementing agent should design installation to match the path documented here. This is what users will follow.

**Path A — Manual copy (simplest, v1.0):**

```bash
# 1. Clone the repo
git clone https://github.com/<user>/context-optimizer.git

# 2. Copy the skill file to Claude Code's skills directory
cp context-optimizer/skill/context-optimizer.md ~/.claude/skills/

# 3. Invoke in any project
cd /path/to/your/project
claude
> /skill context-optimizer
```

**Path B — Curl installer (v1.1+, optional):**

`install.sh` script at repo root that copies the skill file and optionally creates symlinks. Modeled after `claude-code-dotfiles`.

Document only Path A in v1 README; Path B is a v1.1+ enhancement.

## 7. Quality Bar — DX Checks Before Declaring Done

Before declaring the skill complete, verify these DX-specific items. These extend the basic Definition of Done with experience-quality checks.

| DX Check | Pass condition |
|---|---|
| **Concept clarity** | A developer who has never read the spec can read the skill's `Purpose` section and `When to Use This Skill` section and decide whether to invoke it within 60 seconds |
| **First-success time** | A new user, given only the README, can install the skill and run it on their project producing a `context-spec.md` within 5 minutes |
| **Error visibility** | When something goes wrong (e.g., `gh` not authenticated, malformed config file), the skill explains the issue in plain text — never silent, never cryptic |
| **Debuggability** | Every recommendation the skill produces can be traced back to a specific scan signal and a named Known Pattern. If a user asks "why did you recommend this?", the answer is in `context-spec.md` |
| **Friction** | The user is asked 0–3 questions during invocation (per REQ-020 and the weak-state fallback) — never more |
| **Solo dev fit** | A single developer can run the skill, review recommendations, accept/decline, and apply changes — all in one Claude Code session, no external tools needed |

## 8. Post-v1.0 Build Phases (host-native ports — NOT v1.0 scope)

After v1.0 (Claude Code) ships and is validated, the same procedure ports to the other supported hosts. Below is the high-level path. Do NOT execute these as part of v1.0.

### 8.1 v1.1 — Cursor port

**Goal:** Ship the same skill procedure invokable from inside Cursor.

**Steps (summary):**

1. Copy `skill/context-optimizer.md` → `skill/context-optimizer.cursor.mdc`
2. Rewrite the frontmatter to match Cursor's Project Rules format (Cursor uses `.cursor/rules/*.mdc` with its own metadata block)
3. Adapt the invocation guidance — in Cursor there is no `/skill <name>` command; document the actual mechanism (referencing the rule in chat, or auto-applying via rule scope)
4. The Procedure body (5 phases, Known Patterns, layer model) stays **identical** — host-portable by design (C-9)
5. Caveat-line logic in the Implement phase inverts: when running in Cursor, generated `.cursor/rules/*.mdc` carries no caveat; Claude Code / Gemini files (if generated in the same run) get caveat lines
6. Add a new reference project: `examples/project-d-cursor-native/` for validation
7. Validate the same 8 success criteria on the Cursor port (this time, the host = Cursor)

### 8.2 v1.2 — Gemini CLI / Antigravity port

**Goal:** Ship the same skill procedure invokable from inside Gemini CLI / Antigravity.

**Steps (summary):**

1. Copy `skill/context-optimizer.md` → `skill/context-optimizer.antigravity.md`
2. Format for Antigravity's `.agents/skills/SKILL.md` convention
3. For Gemini CLI (no native skill format): document a procedure that users invoke by referencing the skill content from `GEMINI.md`
4. Caveat-line logic inverts again: when running in Gemini/Antigravity, generated `GEMINI.md` files carry no caveat
5. Add reference project: `examples/project-e-gemini-native/`
6. Validate same 8 success criteria

### 8.3 v2.0 — Organic memory growth (deferred)

**Status: DO NOT BUILD UNTIL v1.0 IS IN COMMUNITY USE.**

v2.0 adds the `save_project_fact` tool that enables organic memory growth during normal agent work. Design sketch is in `ARCHITECTURE.md` §13 and `PRD.md` §12.2. v2.0 requires:

- v1.0 shipped and validated on the 3 reference projects
- At least one community user successfully running v1.0 end-to-end on their project
- Telemetry / community feedback identifying which fact-categories emerge most often during work (informs the category enum)
- v1.1 OR v1.2 in some user's hands (so the tool can ship host-native in more than one host from the start)

v2.0 must NOT replace v1.0's scan-first setup. Cold-start (project never optimized) is still owned by v1.0.

### 8.4 Other v1.x candidates (out of scope for v1.0, but worth recording)

- **Curl installer (`install.sh`)** — modeled after claude-code-dotfiles
- **Known Patterns versioning** — track v1, v1.1, v2 patterns separately
- **Pattern contribution workflow** — PR template for new Known Patterns
- **Telemetry (opt-in)** — anonymized `context-spec.md` aggregation for community pattern discovery (would require careful privacy design)
- **Monorepo support** — currently undefined behavior in v1.0; document as known limitation
- **Per-platform behavior verification** — partner with Cursor/Gemini communities to actually test the recommendations, replacing caveat lines with verified guarantees

None of these are blockers for v1.0.0 public release.
